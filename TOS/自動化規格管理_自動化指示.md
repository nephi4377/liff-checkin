# 自動化規格管理｜自動化指示（可貼 Settings）

把下面「指示正文」整段貼進 Cursor Automation 的指令／prompt 欄。  
名稱建議：`自動化規格管理`。觸發：**每天 1 次**（或每 6 小時）。環境：多倉庫 **liff-checkin + Backend_GAS**。

這不是倉庫裡的 cron，而是 [Cursor Automations](https://cursor.com/automations)。  
與「營運系統真人巡檢」分開；**不要**覆寫 `TOS/巡檢回報.md`。

---

## 指示正文

```text
你正在執行「自動化規格管理」。必須遵守專案 Skill：automated-spec-manager
（路徑 .agents/skills/automated-spec-manager/；先讀 SKILL.md、phases.md、檢查維度.md、實作備註.md）。

目標：分階檢查功能 → 建立／升級 SPEC；每輪必查（1）交叉出錯可能性（2）操作易延時判定（3）可改進；
出錯發 Slack #程式撰寫。不是真人巡檢：不以修程式／部署為主業；不要覆寫 TOS/巡檢回報.md。

環境：liff-checkin 與 Backend_GAS 都在工作區。前端根目錄不要 npm install。
未明說部署 → 不 clasp、不 upload。

步驟：
1. 載入持久回報（必做，避免每輪卡在 F1）：
   git fetch origin spec-audit/state（若有）；優先用該分支的 TOS/規格巡檢回報.md。
   若無此分支：比較 origin/main 與未合併 spec-audit/*／[規格管理] PR，取最新一份回報檔。
   用它決定本輪階段（無紀錄則 F1），避開上一輪已查功能 ID。
2. 依 phases.md 在本輪階段挑 1～2 個功能。讀關鍵程式（前端頁＋對應 GAS），再找既有 SPEC。
3. 對每個功能：
   - 無 SPEC → 在合適位置新建（見 Skill「SPEC 放哪裡」）。
   - 有 SPEC 但落後 → 升級（程式為準；明顯 bug 不要寫成正確行為）。
   - 已對齊 → 在回報註明即可。
   流程圖遵守 spec-plain-flowchart（圖內白話、圖下程式對照表）。勿寫金鑰／LIFF ID。
   建議 SPEC 加「風險與等待」小節（交叉摘要＋易延時操作）。
4. 同一功能必做檢查維度.md 三塊（不可跳過）：
   - 交叉出錯：至少 2 個「若…則…」，標已防／未防／不明。
   - 延時判定：低／中／高＋一句依據。
   - 可改進：至少 1 條；或「暫無」＋理由。
5. 發現錯誤／bug → 依 B0～B3 寫進回報。
   **出錯必發 Slack**：B0／B1 → #程式撰寫（channel_id=C0AULCX9SLT）。
   SPEC／小修另開分支與 [規格管理] PR；不上正式、不合 main。
6. 覆寫 TOS/規格巡檢回報.md 後，**立刻 push 到 origin/spec-audit/state**（狀態與 SPEC PR 分開；
   無此分支就建立）。B0／B1／待決寫進「待修／待你決定」。
   不要覆寫 TOS/巡檢回報.md、不要覆寫根目錄 下一輪該改什麼.md。
7. 對話立刻寫結論；結尾固定四行：
   SPEC 已更新：…
   Bug 待看：…
   延時／交叉／改進：…
   下一階指針：…

禁止：一次掃完全庫；沒讀程式就改 SPEC；只改 SPEC 跳過三維度；
把輪替指針只留在未合併 PR；把 bug 當正確規格寫死；複製舊回報交差。
```
