# 裝修施工流程系統 SPEC
版本：v1.1

## 1. 核心定位
本系統不是單純施工 SOP 網站，而是以標準施工流程為母版，讓每一個實際案件建立自己的施工流程、排程、驗收與紀錄。

系統內部可以複雜，但使用者操作必須簡單、直覺、少步驟，符合一般人的操作習慣。使用者不需要理解資料結構、依賴關係、節點 ID 或排程演算法；系統應吸收複雜度並主動提示下一步。

## 2. 架構
### 2.1 標準模板層
- 舊屋翻修模板
- 新屋裝修模板
- 未來可增加局部工程模板

模板可包含完整施工節點、前置條件、驗收點、停檢點、風險、工種與建議工期。

### 2.2 案件層
每個案號建立自己的流程副本，例如 #775、#791。建立案件後從模板複製，不直接修改母版。

案件需至少具有：
- project_id / 案號
- 案名
- 地址
- 案件類型
- 開工日
- 預計完工日
- 工程範圍
- 案件狀態

### 2.3 執行層
每個案件節點可以獨立記錄：
- 是否適用
- 預計日期
- 實際日期
- 負責工班/角色
- 前置工項
- 完成狀態
- 驗收狀態
- 現場照片
- 備註
- 異常
- 是否阻擋下一工序

## 3. 空間維度
流程必須支援空間層級，例如：
#791 → 2F主浴 → 防水 → 第2道防水 → 閉水測試。
避免同案多浴室、多房間、多樓層工作混在一起。

## 4. UX 最高原則
- 後端可以複雜，前端一定要簡單。
- 系統替人思考，不是叫人操作系統。
- 第一次使用的人，不看說明也大致知道怎麼操作。
- 每一個畫面，3 秒內應知道下一步。
- 一次只處理一件主要任務。
- 能選就不要打字。
- 能自動判斷就不要要求使用者手動排序或判斷。
- 詳細資訊採漸進式展開，不一次塞滿。

## 5. 首頁以案件為中心
一般使用者進入後先看到「我的案件」，不是先看到 SOP。

每張案件卡至少顯示：
- 案號與案名
- 整體進度
- 今天工作數
- 卡關數
- 下一階段

主導航原則最多 4~5 個：
- 案件
- 今日
- 問題
- 流程
- 更多

## 6. 案件建立流程
案件建立不超過 3~4 步：
1. 基本資料：案號、案名、地址、開工日、預計完工日
2. 案件類型：舊屋 / 新屋 / 局部工程
3. 工程範圍勾選：拆除、水電、泥作、防水、木作、油漆、系統櫃、地板、廚具、冷氣等
4. 系統自動建立案件施工流程

不要要求使用者一開始設定複雜排程。

## 7. 每日操作核心
案件頁優先回答四件事：
1. 今天要做什麼
2. 哪些事情卡住
3. 接下來做什麼
4. 整體進度

每個工作卡主要操作：
- 完成
- 有問題
- 拍照
- 查看詳細

重要操作位置需一致，建立肌肉記憶。

## 8. 工作節點最低資料要求
每個重要施工節點至少包含：
- 工作名稱
- 所屬階段
- 施工目的
- 前置條件
- 工作內容
- 配合工種
- 驗收條件
- 停檢點
- 拍照要求
- 常見錯誤/風險
- 下一步

## 9. 自動流程與依賴
系統應自行處理：
- 工序排序
- 前置條件
- 下一工項
- 基本施工天數
- 工種關係
- 驗收節點
- 停檢點

例如：
水電配管 → 試壓 → 拍照 → 驗收 → 泥作封管。
若試壓未通過，系統不得建議進入封管。

## 10. 異常處理
任何工作都有「有問題」。
問題類型可快速選：
- 尺寸不符
- 現場條件不同
- 缺料
- 工班未到
- 客戶待確認
- 前工未完成
- 其他

可附照片與一句備註，系統自動標記為卡關，並影響後續工序。

## 11. 角色模式
### 助理
重點：今天要追什麼、要問誰、缺什麼資料。
### 工務
重點：今天施工、卡關、驗收、下一工班。
### 設計師
重點：圖面、尺寸、材料、收口、待確認。
### BOSS
重點：案件進度、延誤、重大問題、未完成驗收、本週進場狀況。

## 12. 舊屋與新屋標準模板
舊屋、新屋必須維持分頁與獨立模板，不得混成同一流程。

舊屋重點：拆除後檢查、結構/漏水/壁癌、全室水電、防水、泥作與大量隱蔽工程。
新屋重點：建商交屋檢查、複尺、局部修改、機電調整、空調、天花、櫃體與設備整合。

## 13. 手機優先
- 單欄卡片為主
- 禁止主要操作依賴橫向大型表格
- 詳細資料可展開
- 今日工作與卡關需最快看到

## 14. 顏色規則
顏色只代表狀態，不作裝飾：
- 灰：未開始
- 藍：準備中
- 黃：施工中
- 橘：待確認
- 紅：卡關
- 綠：完成

## 15. 禁止 UX
- 大量表格
- 多層下拉選單
- 一次十幾個欄位
- 手機左右滑才能操作
- 每次操作都跳視窗
- 讓使用者自行排序工序
- 讓使用者理解節點 ID / dependency 等內部術語
- 一件事情需要進三四層頁面才能完成

## 16. 自動迭代原則
每輪只做小幅、單一主題、可驗證的升級。
優先順序：
1. 補施工節點
2. 補前置條件
3. 補驗收標準
4. 補停檢點
5. 補施工風險
6. 補工種關係
7. 補常見錯誤
8. 改善案件化能力
9. 改善每日操作體驗
10. 改善手機版
11. 補教育內容

每次新增功能必須同時評估：是否讓使用者更簡單。若功能讓一般操作增加不必要步驟，不視為升級。

## 17. 自動迭代禁止事項
- 不得修改其他正式頁面或主控台
- 不得影響 modules/info/onboardingflow.html 等既有正式功能
- 不得刪除既有正確資訊
- 不得把舊屋與新屋重新合併
- 未經確認不得加入登入、複雜後端、正式案件資料寫入
- 未經確認不得直接整合既有 TOS / Backend_GAS 的正式資料流
- 不得為了產生 commit 而硬改

## 18. 現階段檔案範圍
目前只允許優先維護：
- modules/info/renovation-workflow.html
- modules/info/renovation-old-house.html
- modules/info/renovation-new-house.html
- SPEC/裝修施工流程系統_SPEC.md

## 19. 第一階段目標
先做成熟的施工流程與案件化 UX 原型，不急著變成施工 ERP。

目標：
- 舊屋約 150~250 個有效施工節點
- 新屋約 100~180 個有效施工節點
- 能以案件角度套用模板
- 案件首頁能清楚顯示今日、卡關、下一步、進度
- 手機操作簡單明瞭

## 20. 長期目標
逐步擴充：
- 案件
- 日期
- 工班
- 排程
- 進度
- 延誤
- 驗收
- 缺失
- 照片
- 問題追蹤

最終讓系統主動回答：
- 今天這個案場要做什麼？
- 哪一個工班可以進場？
- 還缺什麼才能施工？
- 哪個項目不能封起來？
- 哪裡還沒驗收？
- 今天應該拍哪些照片？
- 哪一個工項可能延誤？
- 下一個工班什麼時候可以進場？

核心原則：人看得懂、現場用得到、系統判斷得了。
