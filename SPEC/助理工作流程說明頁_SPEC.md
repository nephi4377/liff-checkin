# 添心設計｜助理工作流程說明頁 SPEC

> 狀態：Active / Priority
> 建立日期：2026-09-10
> 前端入口：`#/help/assistant-workflow`
> 前端模組：`modules/help/assistant-workflow.html`

## 1. 產品定位

這是一個給助理閱讀與學習的作業標準頁，不是派工、排程、打勾待辦或正式案件資料庫。

現階段先把公司內反覆出現的協助事務整理成「知道何時開始、依什麼順序、要問誰、何時算完成」的流程。流程成熟後，再由豪哥決定是否轉成系統功能。

## 2. 目標

1. 降低口頭交辦造成的漏問、跳步與資訊落差。
2. 讓新進助理能依頁面完成基本工作，不必每次重新詢問完整做法。
3. 統一完成條件，避免把「已詢問」誤當成「已確認／已完成」。
4. 逐步累積訊息範本、異常分支與實際案例。
5. 案件相關紀錄一律以 canonical `project_id` 對應既有資料。

## 3. 非目標與限制

- 不恢復 `#/assistant-workflow` 操作原型入口。
- 不新增 localStorage 任務、不接 GAS、不建立另一套案件或排程資料。
- 不取代 `modules/info/onboardingflow.html` v2.4 的新客接洽流程。
- 不修改 `modules/info/onboardingflow-v2.5-notes.md`、案例頁與 BAK。
- 不把外部廠商的預估答覆寫成公司已確認的承諾。

## 4. 每一種流程的固定結構

每個助理事務至少包含：

1. 適用情境／觸發條件。
2. 開始前必要輸入。
3. 逐步執行順序與前後依賴。
4. 各步驟要詢問或核對的對象。
5. 最終產出與完成條件。
6. 不可省略的確認點。
7. 等待、逾時、取消、異常與退回的處理。
8. 可直接使用的內部／廠商／客戶訊息範本。
9. 應保存的證據、文件位置與版本。

## 5. 共用流程骨架

`收到交辦 → 向內確認範圍 → 向外確認可行性 → 交叉核對限制 → 對客確認 → 同步所有人與留痕`

共用規則：

- 聯絡過不等於完成；必須取得明確答覆或設定下一次追蹤點。
- 回報不得只寫「已處理」，必須包含結果、卡點、待誰決定與下一步。
- 任何涉及客戶的日期、金額、規格，須先完成內部與外部可行性確認。
- 同一事項有版本變更時，必須明確標示最新版本並通知受影響對象。

## 7. 驗收條件

1. 主控台首頁不再顯示可操作的助理工作流卡片。
2. `#/assistant-workflow` 不再是有效 SPA 路由。
3. 使用教學可進入 `#/help/assistant-workflow`。
4. 頁面明確寫出這是說明頁，不是正式派工或排程系統。
5. 手機 390px 不產生橫向捲動；表格在必要時可由容器承接，不擠壓正文。
6. 每種 P0 流程都有必要輸入、步驟、產出、完成條件與不可跳步事項。
7. 不公開真實案件、人名、電話、地址或客戶資料。

## 8. 自動迭代規則

每輪只深化一種助理事務，優先處理 P0 未完成項目：

1. 先拉取最新 `main`，閱讀本 SPEC、`AGENTS.md` 與 `TOS/TOS_AUDIT.md`。
2. 只更新說明頁、共用說明樣式、本 SPEC 與必要的 TOS 追加紀錄。
3. 未經豪哥明確確認，不得恢復操作型工作流、建立後端資料層或新增主控台首頁卡片。
4. 新流程必須源於實際反覆發生的助理事務；沒有足夠資料時先列待釐清，不自行虛構公司規則。
5. 優先補異常分支、完成條件與訊息範本，不以增加頁面字數作為完成。
6. 修改後檢查 HTML、路由、手機版與保護路徑；只有實質改善且測試通過才提交。
7. 完成後更新本 SPEC 勾選並追加一行迭代紀錄。
