# Skill：共享資料庫（tanxin-dev-kb）

> **定稿**（2026-10-13）。正式路徑：`liff-checkin/.agents/skills/shared-dev-kb/SKILL.md`  
> Context 此份與正式檔同步，供本專案對照。

---

## 這個 Skill 的主要用途

讓 Agent **連上並正確使用「共享資料庫」**：

1. **先對齊大項目**——目前階段要做／不做什麼，避免憑記憶或只靠單一對話  
2. **依你的問題查現況**——某條線做到哪、決策是什麼、風險／待決是什麼  
3. **寫入交接**——你要求時必寫；**Agent 判斷有需要時也可以寫**（須遵守下方「寫入規則」）

一句話：這個 Skill 是「怎麼連、怎麼查、怎麼寫」共享資料庫的操作手冊。

---

## 共享資料庫的主要用途

共享資料庫＝GitHub 上的 **`tanxin-dev-kb`**（交接知識庫／開發筆記本）。

它用來記：

| 記什麼 | 放哪裡（概念） |
| --- | --- |
| **大方向**——現階段目標、明確不開工的包 | `goals/` |
| **分類現況與決策**——做到哪、為什麼、LOG | `categories/*/LOG/` 等 |
| **怎麼寫進庫的規則** | `RULES.md` |

它**不是**：

- 給客人用的產品程式（程式在 `liff-checkin`／`Backend_GAS` 等）
- TX34 本機 Hermes／網頁「添心資料庫」（那是給本機 LLM 檢索案場／文件用的）
- 單一 Project 的 Context 暫存（聊天旁邊的筆記；重要結論應再寫進本庫才算進共享庫）

一句話：共享資料庫讓換人、換對話、換 Agent 時，還能從**同一份交接**接續，而不是從頭問你。

## 名稱

`shared-dev-kb`／觸發詞：**共享資料庫**、**tanxin-dev-kb**、**連接共享資料庫**、**看大方向／查現況（共享庫）**

## 管什麼

- 讀寫／查詢 GitHub 交接知識庫 **`nephi4377/tanxin-dev-kb`**
- 先看大方向，或依使用者指定主題查現況

## 不管什麼

- 本機 Hermes 主庫 `tanxin.db`、網頁版 `KnowledgeBase\`（那是 TX34 產品知識庫，不是本 skill）
- Project Context（`/cursor/stores/...`）可當暫存，**不能**代替「已寫進共享資料庫」
- 產品程式部署（clasp／Pages 等）——未明說「部署」不做
- 把聊天流水帳、猜測、未確認的事實寫進庫

## 使用者偏好（固定）

| 說法 | 意思 |
| --- | --- |
| 共享資料庫 | **一律** `tanxin-dev-kb` |
| 說明方式 | 繁體中文白話；少用程式名當主語 |
| 大方向 vs 細節 | `goals/`＝大方向；細節在 `categories/*/LOG/` |
| 共享庫 Git | 寫入後**直接進 main**（見 D4）；不必再等使用者審 PR 後合併 |

## 何時用

使用者說了類似：

- 「連接共享資料庫」
- 「共享資料庫裡有什麼大項目」
- 「共享資料庫查一下 XXX 現況」
- 「把現況寫進共享資料庫」

或 Agent 判斷符合 D1、需主動寫入時。

## 步驟

### A. 連接（每次要查／寫之前）

1. 確認 checkout：優先 `…/tanxin-dev-kb`；沒有就 clone `https://github.com/nephi4377/tanxin-dev-kb`。
2. `git pull`（或 fetch）對齊遠端，避免看舊稿。
3. 先讀：`RULES.md` → `goals/CURRENT.md` → `categories/_index.md`（或各分類 README）。

### B. 預設：先檢視大項目

使用者沒指定主題時，回覆結構：

1. **一句話**：現階段重心是什麼（來自 `goals/CURRENT.md`）。
2. **大方向清單**：每條一句話＋做到哪（未開工／進行中／已完成）。
3. **下一步待拍板**（若目標裡有寫）。
4. 問：要展開哪一條，或要查哪個分類。

### C. 依要求查現況

1. 對應到分類：`accounting`／`hub`／`infra`／`portfolio`／`travel`／`catalog` 等。
2. 讀該分類 `README`＋近期 `LOG/`（必要時 INDEX）。
3. 白話回報：是什麼、做到哪、待決／風險、相關 LOG 檔名（可提路徑，勿整段貼程式）。

### D. 寫入共享資料庫

寫入分兩種觸發，**規則相同**：

| 觸發 | 何時 |
| --- | --- |
| **使用者要求** | 明說「寫進共享資料庫／記進 kb」等 → **應寫** |
| **Agent 主動** | 判斷「不寫進庫，下一位／下一輪會丟關鍵交接」→ **可以寫**，且寫完要在回覆裡用白話說「已寫入共享庫：哪一檔／做了什麼」 |

#### D1. 應該寫入（符合任一條即可）

- 已拍板的**決策**（做／不做、先做哪條、權限門檻等）
- **階段狀態改變**（未開工→進行中→完成／叫停；含「明確不開工」）
- **交接必需**：路徑、環境、停在哪裡、怎麼接續（例如 TX34 路徑、批次進度）
- **風險／待決**已確認且會影響後續（不是臆測）
- 使用者要求留下的驗收重點、正式站對照結論

#### D2. 不要寫入

- 尚未向使用者確認的猜測、草案腦力激盪
- 純聊天寒暄、重複已在庫裡且無新資訊的內容
- 產品程式細節清單（函式名堆疊）——應寫「人能接續的結論」，細節指向產品 repo／PR
- 機密（token、密鑰、個資）——不進本庫
- 把 Project Context 整份搬進庫當備份（只摘**會影響交接的結論**）

#### D3. 寫到哪裡（先讀 `RULES.md`，再對齊）

| 內容性質 | 寫入位置 |
| --- | --- |
| 大方向增刪、現階段重心變了 | `goals/CURRENT.md`（只寫大方向，不寫微任務） |
| 某分類的進度、決策、LOG | `categories/<分類>/LOG/YYYY-MM-DD-….md` |
| 該分類目錄／摘要 | 更新該分類 `INDEX.md`／`README.md`（若慣例有） |
| 分類總覽需指路 | `categories/_index.md`（短指標即可） |

檔名、分類選擇以庫內 `RULES.md` 為準；與現有 LOG 風格一致（白話、可掃讀）。

#### D4. 寫入後怎麼進 Git（共享庫專用）

**範圍：** 僅 `tanxin-dev-kb`。不套用到產品 repo（`liff-checkin`／`Backend_GAS` 等）的一般「沒叫就不要 commit」習慣。

1. **先 pull**，再改，減少衝突。  
2. 工作區改完 → **commit，並直接讓變更進 `main`**（可 `push` 到 `main`，或開 PR 後**立刻合併**，不必等使用者再審一次 PR）。  
3. 回覆使用者時必帶：改了哪些檔（白話）＋已進 `main` 的依據（commit／已合併的 PR 連結）。  
4. 若當下無法推送／合併（權限／離線／衝突）：保留本地改動，白話說明卡住原因與需要你做的一步。  
5. **仍禁止**：未明說「部署」就做產品 clasp／Pages；把密鑰／個資推進庫。

#### D5. Agent 主動寫入時的額外自檢

寫之前問自己（通過才寫）：

1. 這是**已發生或已拍板**的事嗎？還是我猜的？  
2. 不寫的話，換對話／換人會不會接不下去？  
3. 有沒有更合適的分類／是否該只改 LOG 而不動 `goals`？  
4. 有沒有把 TX34 本機庫或 Context 誤當成寫入目標？

### E. 和本機 TX34 的界線

| | 共享資料庫 (本 skill) | TX34 本機庫 |
| --- | --- | --- |
| 是什麼 | Git 交接筆記本 | Hermes／網頁知識庫與檔案 |
| 典型路徑 | GitHub `tanxin-dev-kb` | `…\hermes\tanxin-kb\tanxin.db`、`KnowledgeBase\`、`Dropbox\…\添心資料庫\` |
| 誰跑 | 雲端 checkout 即可讀寫 Git | 必須派 TX34 自架工作機 |

兩邊可互相「指路」，但寫入目標要分清使用者指的是哪一個。

## 回覆形狀（查詢時）

```markdown
## 一句話
（共享庫裡這件事現在怎樣）

## 白話說明
1. …
2. …

## 來源（共享庫）
- goals/… 或 categories/…/LOG/…
```

- [ ] 若有寫入：是否符合 D1、避開 D2？位置是否符合 D3？
- [ ] 若有寫入：變更是否已進 `main`（或已說明無法推送的原因）？
- [ ] Agent 主動寫入時：是否已在回覆說明寫了什麼？
- [ ] 有無誤對產品 repo 部署或把密鑰寫進庫？
- [ ] 說明是否白話？
