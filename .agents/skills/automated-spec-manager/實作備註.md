# 自動化規格管理｜實作備註

給執行本 Skill 的 Cloud Agent／Automation。

## 環境

- 多倉庫：**liff-checkin** + **Backend_GAS**。
- 前端根目錄不要 `npm install`；靜態站用 `npx --yes serve@14` 即可（多數輪次以讀碼為主，不必開站）。
- 排程不是 repo cron，而是 [Cursor Automations](https://cursor.com/automations)。

## Git 與變更範圍

- 產品 repo：SPEC／回報檔改動開分支 `spec-audit/<簡短主題>-YYYYMMDD` 或沿用 Automation 指定分支；push 後可開 PR，標題含 `[規格管理]`。
- **不要**直接推 main（除非使用者／共享庫規則另說；本 Skill 的產品 SPEC 走 PR）。
- 一次 PR 以本輪 1～2 功能的 SPEC＋回報為主；不要夾帶無關重構。
- 未明說「部署」→ 不 clasp、不 upload、不 Pages。

## Slack 回報（出錯必做：B0／B1）

出錯以 **Slack `#程式撰寫`** 為主回報管道（不是可選）。

1. `slack_send_message`，`channel_id`＝`C0AULCX9SLT`（`#程式撰寫`）。
2. 內容模板：

```text
【規格管理・出錯】B0/B1
功能：<白話名>
一句話：…
建議：…
回報檔：liff-checkin/TOS/規格巡檢回報.md
分支或 PR：（有則貼）
```

3. 失敗：重試一次；仍失敗則在對話與 `TOS/規格巡檢回報.md` 註「Slack 未送出：原因」。有 B0／B1 卻完全沒嘗試 Slack＝本輪未完成。

## 讀碼建議順序（單一功能）

1. 找入口頁／主 JS。
2. 找呼叫的 API action 或 GAS 檔。
3. 搜既有 `SPEC/**` 與子專案 SPEC。
4. 比對：人怎麼走、成功／失敗／空、權限。
5. 依 `檢查維度.md` 推演交叉出錯（連點、雙源、部分成功、跨頁快取等）。
6. 判延時：有無整表掃描、timeout、重試、骨架／「更新中」、3～5 秒仍空白。
7. 列可改進（閉環、人話、字典、可測、升級機會）。
8. 寫或升級 SPEC（可加「風險與等待」）→ 更新回報指針；B0／B1 發 Slack。

## 與真人巡檢並存

- 兩套 Automation 可同時開；回報檔不同，勿互相覆寫。
- 節奏建議：規格管理可 **每天 1 次** 或 **每 4～6 小時**（比真人巡檢疏），避免雙重燒額度。
