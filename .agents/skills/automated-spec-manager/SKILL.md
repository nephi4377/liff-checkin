# 自動化規格管理

**一句定位**：依輪替表**分階**檢查功能；程式為準，**建立或升級 SPEC**；發現 bug 要**可回報**（檔案＋可選 Slack），不跟「真人巡檢」搶修程式主場。

與 `system-human-patrol` 的差別：

| | 本 Skill（規格管理） | 真人巡檢 |
|--|----------------------|----------|
| 主目標 | SPEC 齊不齊、與程式一不一致 | 人怎麼踩、失敗當空、體驗 |
| 每輪 | 一階裡 1～2 個功能 | 一視角 1～2 切入點 |
| 改什麼 | 優先改／新建 SPEC | 依 P0～P3 改程式或只建議 |
| 回報檔 | `TOS/規格巡檢回報.md` | `TOS/巡檢回報.md` |

排程設定：[`TOS/自動化規格管理_自動化指示.md`](../../../TOS/自動化規格管理_自動化指示.md)。Dashboard：[`TOS/自動化規格管理_切換步驟.md`](../../../TOS/自動化規格管理_切換步驟.md)。

## 必做順序

1. 讀本目錄 [`phases.md`](phases.md)、[`實作備註.md`](實作備註.md)。
2. 讀 [`TOS/規格巡檢回報.md`](../../../TOS/規格巡檢回報.md)：定**本輪階段**與避開剛查過的同一功能。
3. 從本輪階段挑 **1～2 個功能**（見 phases 選點規則）。
4. 對每個功能：對照程式 ↔ 既有 SPEC → **新建／升級 SPEC**，或記「已對齊」。
5. 過程中若發現 **錯誤／bug**（行為錯、契約破、明顯失敗當空等）→ 走下方「回報方案」；**本 Skill 預設不部署、不 clasp**。
6. 立刻在對話寫結論；並覆寫 `TOS/規格巡檢回報.md` 的「本輪」與輪替指針。
7. 結尾固定摘要三行（見下）。

## 程式為準

- 現行行為以**程式**為準；SPEC 落後就更新 SPEC。
- 程式明顯是 bug（與產品意圖／多處用法矛盾）→ **不要**把 bug 寫進 SPEC 當正確行為；改記 bug 回報，SPEC 可註「已知問題」或保持正確意圖並標待修。
- 流程圖遵守 `.cursor/rules/spec-plain-flowchart.mdc`：圖內白話；圖下「程式對照表」。
- 術語寫入或核對 `SPEC/專有名詞白話對照.md`（短一行即可）。
- 勿把網址、金鑰、LIFF ID 寫進 SPEC。

## SPEC 放哪裡

| 功能落點 | 新建／升級位置 |
|----------|----------------|
| 前端主流程、跨模組、Hub／LIFF 頁 | `liff-checkin/SPEC/`（已有編號／主題檔就升級該檔；沒有則新檔，檔名白話＋`_SPEC.md`） |
| 後端 Checkin／出勤 | `Backend_GAS/CheckinSystem/SPEC/` |
| 後端主控台／日報／訊息 | `Backend_GAS/project-console/SPEC/` |
| 後端會計 GAS | `Backend_GAS/accounting-gas/SPEC/` |
| 已有子專案 SPEC（如 shop-orders） | 該子目錄 `SPEC/`，不要複製到前端根 SPEC 當第二真相 |

前後端同一功能：前端 SPEC 寫人怎麼走；後端 SPEC 寫契約／表／action。兩邊互指路徑即可，**不要**整份複製。

## 本輪產出標準（每個功能）

至少做到：

1. **一句話**：這功能是給誰、做什麼。
2. **人怎麼走**（3～8 步，白話）。
3. **與程式對照**：主要頁面／模組路徑、關鍵 API／action（對照表即可）。
4. **已知落差**：SPEC 舊了哪裡、或缺 SPEC 才新建。
5. 若有 bug：**等級＋人怎麼踩到＋建議**（見下），不可只寫「有問題」。

升級既有 SPEC 時：保留仍正確的段落；改過期段落；文首或文末加一行「最後對照程式：YYYY-MM-DD（Asia/Taipei）」。

## 發現錯誤／bug → 回報方案

本 Skill **以回報為主**，不取代真人巡檢的自動修／部署。

| 等級 | 長相 | Agent 做什麼 |
|------|------|--------------|
| **B0 阻斷** | 主流程錯資料、失敗當成功、權限可繞過且修法清楚 | 寫進回報「本輪」＋「待你決定／待修」；**Slack DM** 通知擁有者；可開分支修程式但不部署、不合 main |
| **B1 明顯缺陷** | 錯誤誤導、無重試、契約與呼叫端不一致 | 同上寫檔；Slack 可合併成一則摘要；建議修法＋驗收 |
| **B2 規格債** | 僅文件過時、缺圖、命名混亂 | 直接升級 SPEC；不必 Slack |
| **B3 建議** | 可讀性、結構、未來拆檔 | 只寫建議 |

Slack：有 B0／B1 時，用 Slack 工具 DM 使用者（預設 `U0AUWBQS62G`／Nephi）。訊息含：功能名、等級、一句話、回報檔路徑、若有分支／PR 連結。無 Slack 權限則對話＋檔案仍算完成，並註明「Slack 未送出」。

**禁止**：未說「部署」就 clasp／upload；把密鑰寫進 SPEC；同一輪假裝掃完全庫；複製貼上舊回報交差。

## 與真人巡檢重疊時

- 同一 bug 若 `TOS/巡檢回報.md` 已有且狀態未變 → 規格回報只**引用**，不重複開修。
- 本輪主業仍是 SPEC；不要為了追 P0 部署而丟下規格更新。

## 回報格式（對話＋檔案）

```text
本輪階段：…
本輪功能：…
SPEC：新建／升級／已對齊（列檔名）
Bug：B0/B1/B2/B3 或無
```

結尾固定三行：

```text
SPEC 已更新：N 件（檔名或「無」）
Bug 待看：N 件（一句話或「無」；有則是否已 Slack）
下一階指針：階段名
```

## 禁止

- 把真人巡檢回報檔當本 Skill 交差檔
- 未讀程式就改寫 SPEC「想像行為」
- 一次掃完整個程式庫（必須分階）
- 覆寫 `下一輪該改什麼.md` 或 `TOS/巡檢回報.md`
