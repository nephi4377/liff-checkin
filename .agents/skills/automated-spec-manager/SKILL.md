# 自動化規格管理

**一句定位**：依輪替表**分階**檢查功能；程式為準，**建立或升級 SPEC**；每輪必做**交叉出錯推演、延時判定、可改進**；出錯發 Slack `#程式撰寫`。不跟「真人巡檢」搶修／部署主場。

與 `system-human-patrol` 的差別：

| | 本 Skill（規格管理） | 真人巡檢 |
|--|----------------------|----------|
| 主目標 | SPEC＋風險維度（交叉／延時／改進） | 人怎麼踩、失敗當空、體驗 |
| 每輪 | 一階裡 1～2 個功能 | 一視角 1～2 切入點 |
| 改什麼 | 優先改／新建 SPEC；bug 以回報＋Slack 為主 | 依 P0～P3 改程式或只建議 |
| 回報檔 | `TOS/規格巡檢回報.md` | `TOS/巡檢回報.md` |

排程設定：[`TOS/自動化規格管理_自動化指示.md`](../../../TOS/自動化規格管理_自動化指示.md)。Dashboard：[`TOS/自動化規格管理_切換步驟.md`](../../../TOS/自動化規格管理_切換步驟.md)。  
檢查維度細節：[`檢查維度.md`](檢查維度.md)。

## 必做順序

1. 讀本目錄 [`phases.md`](phases.md)、[`檢查維度.md`](檢查維度.md)、[`實作備註.md`](實作備註.md)。
2. **先載入持久回報**（見實作備註「狀態與 SPEC 分開」）：優先 `origin/spec-audit/state` 的 [`TOS/規格巡檢回報.md`](../../../TOS/規格巡檢回報.md)，再否則 main／未合併 audit 分支中最新一份。用它定**本輪階段**與避開剛查過的功能。
3. 從本輪階段挑 **1～2 個功能**（見 phases 選點規則）。
4. 對每個功能：對照程式 ↔ 既有 SPEC → **新建／升級 SPEC**，或記「已對齊」。
5. **同一功能必做三維度**（見 `檢查維度.md`）：交叉出錯至少 2 情境、延時等級、至少 1 條可改進。
6. 過程中若發現 **錯誤／bug**（含未防交叉、高延時無配套）→ 走下方「回報方案」；**本 Skill 預設不部署、不 clasp**。
7. 立刻在對話寫結論；覆寫 `TOS/規格巡檢回報.md` 的「本輪」與輪替指針，並 **push 到 `spec-audit/state`**（不等 SPEC PR 合併）。SPEC 本體另開 `[規格管理]` PR。
8. 結尾固定摘要四行（見下）。

## 程式為準

- 現行行為以**程式**為準；SPEC 落後就更新 SPEC。
- 程式明顯是 bug（與產品意圖／多處用法矛盾）→ **不要**把 bug 寫進 SPEC 當正確行為；改記 bug 回報，SPEC 可註「已知問題」或保持正確意圖並標待修。
- 流程圖遵守 `.cursor/rules/spec-plain-flowchart.mdc`：圖內白話；圖下「程式對照表」。
- 術語寫入或核對 `SPEC/專有名詞白話對照.md`（短一行即可）。
- 勿把網址、金鑰、LIFF ID 寫進 SPEC。

## SPEC 放哪裡

| 功能落點 | 新建／升級位置 |
|----------|----------------|
| 前端主流程、跨模組、Hub／LIFF 頁 | `liff-checkin/SPEC/`（已有編號／主題檔就升級該檔；沒有則新檔，檔名白話＋`_SPEC.md`） |
| 後端 Checkin／出勤 | `Backend_GAS/CheckinSystem/SPEC/` |
| 後端主控台／日報／訊息 | `Backend_GAS/project-console/SPEC/` |
| 後端會計 GAS | `Backend_GAS/accounting-gas/SPEC/` |
| 已有子專案 SPEC（如 shop-orders） | 該子目錄 `SPEC/`，不要複製到前端根 SPEC 當第二真相 |

前後端同一功能：前端 SPEC 寫人怎麼走；後端 SPEC 寫契約／表／action。兩邊互指路徑即可，**不要**整份複製。

## 本輪產出標準（每個功能）

至少做到：

1. **一句話**：這功能是給誰、做什麼。
2. **人怎麼走**（3～8 步，白話）。
3. **與程式對照**：主要頁面／模組路徑、關鍵 API／action（對照表即可）。
4. **已知落差**：SPEC 舊了哪裡、或缺 SPEC 才新建。
5. **交叉出錯**：至少 2 個「若…則…」情境，標已防／未防／不明（`檢查維度.md` A）。
6. **延時判定**：`低`／`中`／`高`＋一句依據；高且無等待／重試配套要進 Bug（`檢查維度.md` B）。
7. **可改進**：至少 1 條（或「暫無」＋理由）（`檢查維度.md` C）。
8. 若有 bug：**等級＋人怎麼踩到＋建議**（見下），不可只寫「有問題」。

升級既有 SPEC 時：保留仍正確的段落；改過期段落；文首或文末加一行「最後對照程式：YYYY-MM-DD（Asia/Taipei）」。  
建議在 SPEC 加一小節「風險與等待」（交叉風險摘要＋易延時操作），有才寫、勿灌水。

## 發現錯誤／bug → 回報方案

本 Skill **以回報為主**，不取代真人巡檢的自動修／部署。

| 等級 | 長相 | Agent 做什麼 |
|------|------|--------------|
| **B0 阻斷** | 主流程錯資料、失敗當成功、權限可繞過；交叉出錯會寫壞／誤導且修法清楚 | 寫進回報「本輪」＋「待修」；**必須 Slack**（見下）；可開分支修程式但不部署、不合 main |
| **B1 明顯缺陷** | 錯誤誤導、無重試、契約不一致；**高延時**且乾等／無再試；明顯未防交叉 | 同上寫檔；**必須 Slack**（可與同輪其他 bug 併成一則）；建議修法＋驗收 |
| **B2 規格債** | 僅文件過時、缺圖、缺風險小節、命名混亂 | 直接升級 SPEC；不必 Slack |
| **B3 建議** | 可讀性、結構、體驗升級、可測性、合併讀表等可改進 | 只寫建議；不必 Slack |

### 出錯回報＝Slack（必做）

凡本輪有 **B0／B1**（程式錯誤、行為 bug、契約破），**一定要發 Slack**，不能只寫倉庫檔交差。

| 項目 | 值 |
|------|-----|
| 頻道 | `#程式撰寫`（`C0AULCX9SLT`） |
| 工具 | Slack `slack_send_message`，`channel_id`＝`C0AULCX9SLT` |
| 何時 | 每輪有 B0／B1 時；同輪多筆可併成一則 |

訊息模板：

```text
【規格管理・出錯】B0/B1
功能：…
一句話：…
建議：…
回報檔：liff-checkin/TOS/規格巡檢回報.md
分支或 PR：（有則貼）
```

Slack 送失敗：對話＋回報檔註明「Slack 未送出：原因」，並重試一次；仍失敗才算本輪缺口。

**禁止**：未說「部署」就 clasp／upload；把密鑰寫進 SPEC；同一輪假裝掃完全庫；複製貼上舊回報交差。

## 與真人巡檢重疊時

- 同一 bug 若 `TOS/巡檢回報.md` 已有且狀態未變 → 規格回報只**引用**，不重複開修。
- 本輪主業仍是 SPEC；不要為了追 P0 部署而丟下規格更新。

## 回報格式（對話＋檔案）

```text
本輪階段：…
本輪功能：…
SPEC：新建／升級／已對齊（列檔名）
交叉出錯：…（已防／未防）
延時判定：低｜中｜高 — …
可改進：…
Bug：B0/B1/B2/B3 或無
```

結尾固定四行：

```text
SPEC 已更新：N 件（檔名或「無」）
Bug 待看：N 件（一句話或「無」；B0／B1 須註已送 #程式撰寫 或未送出原因）
延時／交叉／改進：各一句摘要或「無新發現」
下一階指針：階段名
```

## 禁止

- 把真人巡檢回報檔當本 Skill 交差檔
- 未讀程式就改寫 SPEC「想像行為」
- 一次掃完整個程式庫（必須分階）
- 只更新 SPEC、**跳過**交叉／延時／可改進三維度
- 覆寫 `下一輪該改什麼.md` 或 `TOS/巡檢回報.md`
